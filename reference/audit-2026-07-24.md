# Multi-tenancy audit — 2026-07-24

A 158-agent audit of every RLS-bypassing path (service-role routes, SECURITY
DEFINER functions, full policy coverage, the money/books paths, the auth
boundary). **38 defects survived three-lens adversarial verification; 12 were
refuted.** Everything that mattered is fixed. This file exists so the same
mistakes aren't reintroduced.

## The two recurring mistakes

### 1. RLS does not protect service-role or SECURITY DEFINER code
`createServiceClient()` and `SECURITY DEFINER` functions bypass RLS **entirely**.
Every read and write on those paths has to scope itself, in code. Actual bugs:

- Read every user's rows, then act on / notify only the owner — a member's
  watchlist alert pushed to the owner, naming a card that wasn't his, while the
  member got nothing.
- A `Map` keyed by a non-unique column across users, so one user's pricing
  template silently applied to another user's cards.
- `.maybeSingle()` on a row that had become per-user — it ERRORS once two users
  each have one, and the error was swallowed by a `catch`.
- A row written with no `user_id` under the service role (`auth.uid()` is NULL
  there) against a table whose RLS requires `user_id = auth.uid()` — invisible
  forever. This silently froze the portfolio/NAV chart.
- `has_card_access()` used as row scoping. **It is an app-ENTRY gate only.**

### 2. PostgREST silently caps a request at 1000 rows
`.limit(20000)` reads like a safety ceiling and behaves like a lie. It bit this
codebase in ~15 places, including:

- a DELETE-then-rebuild of the card-sale ledger that destroyed the rows it never
  read;
- a journal CSV "export" that returned the first 1000 lines with HTTP 200 and no
  signal, with the cut able to land mid-transaction;
- the push preview undercounting "ready" — and able to DISABLE a business's Post
  button, making those entries unpostable from the only UI that posts them;
- realized-gain YTD shown as fact at a fraction of the truth, then cached.

**Use `readAll` / `readAllSafe` from `src/lib/supabase/page.ts`** for anything
feeding a SUM, COUNT, membership Set, idempotency guard, or destructive rebuild.
A plain `.limit()` is fine only for a "most recent N" display list. Pagination
needs a deterministic `.order()` — include a unique tiebreaker.

## The worst one found

The **public showcase published every user's inventory.** `/showcase/[token]` is
unauthenticated and reads with the service role, and never filtered cards by the
showcase's owner. The group picker's DEFAULT option ("All live cards") stores an
empty `card_ids`, which took the fallback branch and returned the 200 most
recent live cards **across all users** — player, set, grade, serial, value, plus
signed photo URLs — to anyone holding the link. Symmetric in both directions.

## Deliberately NOT fixed (low value)

- Duplicate comps from a fail-open dedup read: needs a transient failure, blast
  radius is the caller's own card, and the sibling path already guards it.
- `card_lot_items` / `card_group_items` scope on `owns_card(card_id)` but leave
  `lot_id`/`group_id` unconstrained — needs an out-of-band UUID no screen
  exposes. Worth hardening if that area is touched anyway.
- A group-backed showcase silently caps at 300 cards while the manager UI shows
  the true count.

## Standing rule

Any cron or definer function reading `card_*` must filter by `user_id`
explicitly and page its reads. RLS will not save you there.
